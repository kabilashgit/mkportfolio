Understanding SSR, SSG, and ISR in Next.js

Master the three core rendering strategies in Next.js to build lightning-fast, SEO-friendly web applications with optimal user experience.

Next.js revolutionized React development by offering multiple rendering strategies out of the box. But with SSR, SSG, and ISR, how do you choose the right one? Let's demystify each approach and discover when to use them 🚀

🤔 The Rendering Landscape

Before Next.js, React apps were typically rendered on the client side—JavaScript downloads, executes, and then renders the page. This works but has downsides:

  • ⏱️ Slower initial page load (blank screen while JS loads)
  • 🔍 Poor SEO (search engines struggle with client-rendered content)
  • 📱 Bad experience on slow networks or devices
  • ♿ Accessibility issues for users with JS disabled

Next.js gives you three powerful strategies to solve these problems, each optimized for different scenarios.

🖥️ SSR: Server-Side Rendering

📖 What is SSR?

Server-Side Rendering generates HTML on the server for every request. When a user visits your page, the server:

  1. Fetches necessary data
  2. Renders the React component to HTML
  3. Sends fully-formed HTML to the browser
  4. React "hydrates" the page (makes it interactive)

When to Use SSR?

  • ✓ Pages with frequently changing data (dashboards, feeds)
  • ✓ Pages requiring user-specific content (personalized pages)
  • ✓ Pages needing authentication checks before render
  • ✓ When you need real-time SEO with fresh content
// pages/dashboard.js
export default function Dashboard({ user, stats }) {
  return (
    <div>
      <h1>Welcome, {user.name}!</h1>
      <div>Orders Today: {stats.ordersToday}</div>
      <div>Revenue: ${stats.revenue}</div>
    </div>
  );
}

// Runs on EVERY request
export async function getServerSideProps(context) {
  const { req } = context;
  
  // Check auth, get user
  const user = await getUserFromCookie(req);
  if (!user) {
    return { redirect: { destination: '/login' } };
  }
  
  // Fetch latest stats
  const stats = await fetchLiveStats(user.id);
  
  return {
    props: { user, stats }
  };
}

⚠️ Caution: SSR can be slower than SSG because each request waits for server rendering. Use caching strategies (e.g., Cache-Control headers) to improve performance.

📄 SSG: Static Site Generation

📖 What is SSG?

Static Site Generation pre-renders pages at build time. HTML is generated once during npm run build and reused for all requests. The result:

  • ⚡ Lightning-fast page loads (static HTML served directly)
  • 💰 Lower server costs (just serving files, no compute)
  • 🌍 Perfect for CDN distribution
  • 🔍 100% SEO-friendly (crawlers see full HTML immediately)

When to Use SSG?

  • ✓ Marketing pages, blogs, documentation
  • ✓ Product pages (if catalog doesn't change frequently)
  • ✓ Landing pages and portfolios
  • ✓ Any content that's the same for all users
// pages/blog/[slug].js
export default function BlogPost({ post }) {
  return (
    <article>
      <h1>{post.title}</h1>
      <div dangerouslySetInnerHTML={{ __html: post.content }} />
    </article>
  );
}

// Runs at BUILD time only
export async function getStaticProps({ params }) {
  const post = await fetchPostBySlug(params.slug);
  
  return {
    props: { post },
    revalidate: 3600 // Optional: ISR (more on this below)
  };
}

// Tell Next.js which paths to pre-render
export async function getStaticPaths() {
  const posts = await fetchAllPosts();
  
  return {
    paths: posts.map(post => ({
      params: { slug: post.slug }
    })),
    fallback: 'blocking' // Or false, or true
  };
}

💡 Pro tip: SSG is the default and recommended approach in Next.js. "Can this page be pre-rendered ahead of a user's request?" If yes, use SSG!

🔄 ISR: Incremental Static Regeneration

📖 What is ISR?

ISR is the best of both worlds. It starts with static pages (like SSG) but allows you to update them in the background without rebuilding the entire site.

How it works:

  1. Initial request serves the static page (fast!)
  2. After revalidate seconds, Next.js marks the page as stale
  3. Next request triggers background regeneration
  4. New version replaces old one once ready

When to Use ISR?

  • ✓ E-commerce product pages (prices change occasionally)
  • ✓ News sites (articles updated periodically)
  • ✓ Social feeds (content refreshes but not real-time critical)
  • ✓ Large sites where full rebuilds take too long
// pages/products/[id].js
export default function Product({ product }) {
  return (
    <div>
      <h1>{product.name}</h1>
      <p>Price: ${product.price}</p>
      <p>Stock: {product.stock} units</p>
    </div>
  );
}

export async function getStaticProps({ params }) {
  const product = await fetchProduct(params.id);
  
  return {
    props: { product },
    // Regenerate page every 60 seconds
    revalidate: 60
  };
}

export async function getStaticPaths() {
  return {
    paths: [], // Generate pages on-demand
    fallback: 'blocking' // SSR first visit, then cache
  };
}

✨ Magic moment: ISR gives you static performance with dynamic freshness. Users always get fast pages, but content stays current!

📊 Quick Comparison Table

Feature SSR SSG ISR
Render Time Per request Build time Build + background
Speed Slower (server wait) ⚡ Fastest ⚡ Very fast
Data Freshness 🟢 Real-time 🔴 Stale until rebuild 🟡 Periodic updates
Hosting Cost Higher (compute) Lower (static files) Low-Medium
Best For User dashboards Blogs, docs E-commerce, news

🎯 Decision Tree: Which One Should I Use?

✓ Start with SSG (default)

Can you pre-render this page before a user requests it? → SSG

✓ Need occasional updates?

Content changes but not every second? → ISR

✓ Need real-time data or auth?

Must be fresh for every user on every request? → SSR

✓ Hybrid approach?

Mix strategies! Use SSG for shell, client-side fetch for dynamic parts

🚀 Real-World Example: E-commerce Site

Here's how I'd structure a typical e-commerce site:

  • SSG: Homepage, category pages, about/contact → Static, rarely changes
  • ISR: Product pages → Prices/stock update hourly (revalidate: 3600)
  • SSR: User cart, checkout, account dashboard → Personalized, requires auth
  • Client-side: Search results, filters → Interactive, doesn't need SEO

💡 Key Takeaways

  • 🎯 Default to SSG for maximum performance and lowest cost
  • 🔄 Upgrade to ISR when you need periodic freshness without rebuilds
  • ⚡ Use SSR sparingly for truly dynamic, personalized content
  • 🧩 Mix strategies within the same app—each page can use a different approach
  • 📊 Monitor performance and adjust strategies based on real usage patterns
